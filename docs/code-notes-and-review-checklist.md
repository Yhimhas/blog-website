# 代码注意事项与 Review 清单

适用背景：有 React 和 C++ 基础，学习 Vue 与 Go；每天两小时亲手开发个人博客和每日音乐推荐。

配套：[每日开发计划](./daily-development-learning-plan.md) · [原始方案](./personal-website-development-plan.md)

以下是未来实现时的自查项目，不是对现有代码已经存在问题的断言。当前只发现初始 Vue 骨架，尚没有业务代码可做缺陷 Review。按每日计划中的编号阅读，不需要第一天全部记住。

## 1. React → Vue：优先注意的差异

| React 中熟悉的概念 | Vue 中的切入点 | 容易误用的地方 |
|---|---|---|
| useState | ref、reactive | Vue 的响应式更新机制不同；不要机械照搬 setState 方式 |
| 渲染时派生值、useMemo | computed | 先表达派生关系，不用 watch 复制一份可计算状态 |
| useEffect | watch、watchEffect、生命周期 | 不是一对一映射；先区分派生值、副作用和挂载动作 |
| props 与回调 | props 与 emits | 子组件通过事件请求父组件改变数据 |
| JSX | template 和指令 | 列表 key、表单绑定、条件渲染需要掌握模板规则 |
| 自定义 Hook | composable | 复用有明确目的的逻辑，避免提前抽一个万能封装 |
| 全局状态库 | Pinia | 本项目先用于播放器，不把所有接口响应都存进去 |

### F01：ref、reactive 与解构

- 脚本中通常通过 `.value` 读取和修改 ref；模板会对顶层 ref 做自动解包，但数组、集合和嵌套访问存在例外。
- `reactive` 对象的基本类型属性直接解构为普通变量后，会失去原来的响应式联系。先保留对象访问，确需解构时理解 `toRefs`。
- 不要把普通对象拷贝与响应式对象当成同一个状态来源。
- Vue 3.5+ 的 `defineProps` 响应式解构有编译器专门支持；不能把它的行为推广到所有对象。

自查：筛选词或按钮状态变了，依赖它的界面是否同步更新？参考 [Vue 响应式基础](https://vuejs.org/guide/essentials/reactivity-fundamentals.html)、[Props 响应式解构](https://vuejs.org/guide/components/props.html#reactive-props-destructure)。

### F02：computed 表达派生值，watch 处理副作用

匹配文章数、筛选后的列表、按钮说明等优先写成 computed。computed getter 不发送请求、不修改源状态。需要因状态改变而保存偏好或触发外部动作时，再考虑 watch。

自查：同一信息是否保存成了两份，必须依靠多个 watch 手动保持一致？参考 [Vue computed](https://vuejs.org/guide/essentials/computed.html)。

### F03：数据由拥有它的组件修改

文章卡片接收文章信息并发出事件，父组件处理选择或编辑。不要在子组件中修改 props，也不要借着 props 内嵌对象“可以被修改”就偷偷改父状态。

自查：能否指出每个可变状态的唯一主要维护者？参考 [Vue 单向数据流](https://vuejs.org/guide/components/props.html#one-way-data-flow)。

### F04：列表身份和表单值要稳定

- 文章用稳定 ID 或 slug 作为 key；有筛选、排序和编辑行为的列表不用数组下标代表业务身份。
- 表单里的数字可能仍然是字符串；先处理空值，再做明确转换和验证。
- 分类/标签选择保存业务 ID，避免将显示名称当作关联键。

自查：切换排序后，选中项和输入内容会不会跑到另一张卡片上？

### F05：TypeScript 类型不验证网络数据

不要通过 `any`、大量非空断言或强制类型断言掩盖错误。接口响应在运行时可能缺字段，错误响应也可能没有业务数据；根据 API 契约处理空值和错误。现有工程启用了 `noUncheckedIndexedAccess`，数组下标访问应考虑越界。

自查：接口返回空数组、null 或失败响应时，界面是否崩溃？输入字符长度的规则是否与 Go 一致？

### F06：为异步操作设计完整状态

页面区分 loading、error、empty 和 success。提交失败保留用户输入，保存中避免重复提交；快速切换 slug 或筛选时，用取消或请求序号避免旧结果覆盖新结果。

自查：停止 Go 服务、放慢网络、快速切换文章时，用户能否理解当前状态并重试？

### F07：Nuxt 有服务端和浏览器两个运行环境

- 页面初始数据优先使用 Nuxt 的 `useFetch`/`useAsyncData`；按钮点击触发的写操作可用 `$fetch`。理解各自职责后再封装。
- `window`、`document`、`localStorage` 不存在于服务端；播放器等浏览器能力在合适的客户端阶段初始化。
- SSR 首屏不要依靠不可控随机数、本地时区或仅浏览器存在的值生成不同 HTML，避免 hydration 不一致。
- 公开博客正文不能只在 onMounted 后才加载，否则不符合本方案的 SSR 目标。

自查：直接打开详情 URL、刷新、站内导航三种方式是否都正确？参考 [Nuxt 数据获取](https://nuxt.com/docs/4.x/getting-started/data-fetching)、[Hydration](https://nuxt.com/docs/4.x/guide/best-practices/hydration)。

### F08：SSR 认证和缓存不能串用户

浏览器通过同域 `/api/v1` 访问 Go；SSR 通过受控内部地址访问 Go。私有 SSR 请求若需要 Cookie，只转发给明确受信任的 Go 服务，不能顺手发给任意外部地址。当前会话响应、管理页面和草稿预览不进入共享缓存。

在 Nuxt 模块顶层创建跨请求共享的可变用户状态可能导致请求间泄露；使用框架支持的请求隔离状态管理方式。路由守卫只是界面行为，真正权限判断仍由 Go 完成。参考 [Nuxt 状态管理](https://nuxt.com/docs/4.x/getting-started/state-management)。

自查：一个登录的管理窗口和一个匿名窗口同时打开，匿名窗口能否看到任何管理数据？

### F09：播放器状态和播放器实例分开理解

Pinia 保存当前曲目、队列和偏好，不意味着 iframe 实例会自动存活。PlayerShell 要放在稳定的公共布局位置，不随文章页面卸载；避免给它绑定每次路由变化的 key。iframe 不是普通可精确控制的 audio 元素。

自查：有声播放时切换两次站内文章，实例是否重建？如果进入另一种布局或整页刷新会重载，应清楚说明边界。

### F10：最基本的页面可用性

交互使用合适的 button/link；表单有 label；键盘焦点可见；错误提示靠近对应字段。长代码块只在自身区域横向滚动，固定播放器不遮住最后一段正文。图片缺失有替代信息。

自查：只使用键盘，能否打开文章、输入登录信息并触发播放入口？

## 2. C++ → Go：不要只翻译语法

### G01：值、指针、零值和字符串

Go 的 struct 和数组赋值会复制值；指针用于共享和修改特定对象，不需要进行手动 delete。字符串长度按字节计算，中文“字符数”的业务限制要单独定义，可按 Unicode code point 计数；前端与后端应采用一致规则。

自查：函数是有意修改调用者的数据，还是只处理副本？空字符串、0、false 是有效值还是“没传”？

### G02：error 是正常返回路径

输入错误、查无记录、连接失败都应有明确处理。不要用 `_` 忽略重要 error，也不要用 panic 处理用户输入。包装错误时保留可判断的原因；HTTP 层转换成稳定的外部错误，不直接输出数据库信息。

自查：每个可能失败的调用，调用者能否知道失败并停止不应继续的操作？

### G03：slice 不等于 vector，map 不保证顺序

slice 是对底层数组的描述，复制 slice 可能仍共享底层存储；在排序、打乱推荐候选时，确认是否应先复制。append 的结果要接住，扩容可能改变底层数组。map 的遍历顺序不能用于稳定展示或推荐排序，普通 map 也不应在缺少同步时并发读写。

自查：推荐函数运行后，调用者的原始候选顺序有没有被意外改变？去重后是否仍保留约定顺序？

### G04：defer 不等于 C++ 的块作用域析构

defer 在所在函数返回时运行，不是离开任意花括号就运行。资源获取成功后再安排释放；循环中积累文件或响应体的 defer 可能拖到整个函数退出，按次处理时可以拆成小函数。defer 的参数在登记时求值。参考 [Go defer](https://go.dev/blog/defer-panic-and-recover)。

自查：HTTP 响应体、数据库 rows、取消函数在所有返回路径上是否释放？

### G05：包、interface 和 JSON 可见性

Go 用方法集合隐式满足 interface；只有实际需要替换或测试隔离时才抽接口。字段导出与首字母大小写有关，JSON tag 不能让未导出字段自动变成公开字段。注意 `:=` 在内部作用域可能遮蔽外层变量，尤其是 err。

自查：接口是不是只有一个巨型实现而没有清楚的替换目的？JSON 丢字段时是否先检查导出规则？

以上语言基础可参考 [Go 教程入口](https://go.dev/doc/tutorial/) 和 [Effective Go](https://go.dev/doc/effective_go)；后者是较早的核心语言资料，不用于判断最新工具链或全部现代特性。

### G06：context、超时和 goroutine 生命周期

普通请求将 request context 传给数据库和上游 HTTP 调用；外部操作设置超时。不要在 handler 中随手启动 goroutine 后立即返回，并继续使用已结束的请求上下文或 Gin Context。后台任务应有自己的受控生命周期、持久状态和停止机制。

先写顺序逻辑，推荐调度阶段再学所需并发。每一个 goroutine 都能回答“谁启动、何时退出、失败怎么被观察”。参考 [Go 取消数据库操作](https://go.dev/doc/database/cancel-operations)。

### G07：长期运行服务与命令行题解不同

main 负责组装依赖、配置超时、启动和优雅退出；收到停止信号后停止接收新工作，限时等待已有请求和任务。日志记录 request ID/任务 ID 和错误原因，不记录密码、Cookie 或完整敏感请求。

自查：停止服务时，是直接丢弃工作，还是有可解释的收尾过程？数据库不可用时服务是否仍误报完全就绪？

### G08：按真实职责拆分

handler 处理 HTTP，service 处理发布/推荐规则，repository 处理数据库。先有实际职责再拆文件，不给每张表机械配齐空壳层，也不引入通用仓储和微服务来练抽象。

学习 Gin 时可读 [Go 官方 Gin 教程](https://go.dev/doc/tutorial/web-service-gin)，但教程中的演示数据和省略步骤不能直接当成本项目上线实现。

## 3. SQL、GORM 与数据一致性

### D01：数据库约束是最后一道一致性保证

文章 slug、平台内容身份、推荐业务日期分别建立合适的唯一约束；清单关联和标签关联维护外键及唯一性。Go 中“先查再插”不能代替数据库约束。SQL 使用参数绑定，排序列等不能绑定的结构部分使用允许列表。正式结构由编号迁移维护，不依赖生产启动时 AutoMigrate。

自查：两个请求同时创建同一个 slug，会不会产生重复记录？参考 [PostgreSQL 约束](https://www.postgresql.org/docs/current/ddl-constraints.html)。

### D02：PATCH 缺省值与显式零值不同

“不修改摘要”与“把摘要设为空”必须区分。DTO 可根据字段语义使用指针或显式可选类型，再按允许字段更新。GORM 用 struct 执行 Updates 时默认忽略零值，false/0/空字符串可能没有写入；选择明确字段或经校验的 map，并理解 null 的约定。

自查：将启用状态从 true 改成 false、将摘要清空，刷新后是否真的保存？参考 [GORM 更新](https://gorm.io/docs/update.html)。

### D03：一件业务要么完整成功，要么不生效

文章与标签关联、推荐主记录与子项等需要事务。事务开始后的读写统一通过同一个事务对象执行，不混用全局连接。数据库锁也要在正确的事务与连接中使用。外部平台 HTTP 请求不放进长时间持锁的数据库事务。

自查：故意让最后一个子项写入失败，前面的记录是否一起回滚？参考 [Go 事务](https://go.dev/doc/database/execute-transactions)。

### D04：时间戳和业务日期分开

事件时间使用带时区语义的时间戳并统一按 UTC 处理；“今天”在服务端按 Asia/Shanghai 计算，存为业务日期。不要用浏览器日期决定所有访客的推荐，也不要依赖服务器当前默认时区。明确文章首次发布与修改时间的含义。

自查：UTC 尚未跨日、上海已经跨日时，读取的推荐是哪一天？空发布时间是否会被错误显示成零时间？

## 4. API、登录与 Markdown

### H01：输入 DTO 与数据库模型分开

请求不能直接绑定到包含所有字段的数据库模型，以免客户端修改状态、所有者等未授权字段。后端再次校验长度、枚举、日期、URL 和批量大小；限制请求体。错误形状一致，但保留正确的 HTTP 状态码，例如 400、401、403、404、409、500。

自查：伪造前端没有提供的字段时，后端是否会意外接受？

### H02：密码使用成熟哈希方案

不存明文密码，不使用 MD5/SHA-256 直接哈希密码。优先按维护良好的实现和当前建议使用 Argon2id 等专用密码哈希方案，参数在实际实施时确认并测量。首次站长创建不通过公开注册；登录失败信息不泄露账号存在性，并设置合理限流。参考 [OWASP 密码存储](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)。

自查：读取数据库或日志时，能否直接获得可登录的密码？

### H03：会话真正由 Go 验证

使用密码学安全随机数生成不透明 session token，数据库保存 token 哈希和过期时间。生产 Cookie 使用 HttpOnly、Secure 和适合本站的 SameSite；本地 HTTP 与生产 HTTPS 配置分别验证。注销使服务端会话失效。管理写请求按同源架构落实 Origin/CSRF 校验；不要认为 SameSite 就解决了所有问题。

自查：绕过前端直接调用 API，匿名、过期和注销后的请求是否被拒绝？参考 [OWASP 会话管理](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)。

### H04：Markdown、草稿、缓存要一起检查

v-html 不会自动让不可信 HTML 变安全；Markdown 解析后还要按清洗策略处理脚本、危险链接和属性。默认不开放任意原始 HTML、脚本或 MDX 执行。公开查询在 Go 中明确限制已发布状态；草稿预览受认证保护，并禁止索引和共享缓存。

自查：猜中草稿 slug、打开预览地址、提交危险 Markdown 时分别会发生什么？参考 [Vue 安全](https://vuejs.org/guide/best-practices/security.html)。

### H05：契约和公开输出保持克制

每增加或修改接口，同步字段、分页、空值、错误和权限说明。公开 DTO 不包含 password_hash、session_hash、内部同步错误或服务器路径。分页数量有上限、排序有稳定的第二排序键，历史日期查询限制范围。OpenAPI 生成的 TypeScript 类型仍不取代运行时验证。

自查：前端与后端对空列表、404、空时间和 ID 类型是否有相同理解？

## 5. 音乐来源与播放器

### M01：内容元数据、同步、播放是三种能力

能拿到标题不代表能自动同步整张清单，更不代表能提取完整音频。按平台分别记录能力。条目身份使用规范化平台 ID；Bilibili 多分 P 的页码/cid 规则需要明确，避免错误去重。

自查：UI 是否把“有官方入口”误说成“站内可完整播放”？本计划没有承诺尚未验证的平台能力。

### M02：来源输入不是任意 URL 代理

只接受支持的平台、ID 和允许的官方 URL，服务端构造受控请求地址并校验跳转。不要下载用户输入的任意 URL，也不要接受任意 iframe HTML。调用平台设置超时、范围和数量上限；不以私人 Cookie 或逆向音频解析作为上线基础。

自查：输入本机、内网或不支持的网站地址时，后端是否拒绝？

### M03：失败保留最后成功数据，停用语义明确

来源失败只更新状态和错误摘要，不清空曲目库。条目全局不可用、清单被停用、某清单中的关联被停用是三种不同状态。推荐快照和历史记录不因一次来源失败而被改写。

自查：同一曲目属于两张清单，停用其中一张时是否仍按规则可参与另一张清单？

### M04：播放器能力必须通过真实浏览器验证

首播依赖用户交互；第三方 iframe 的暂停、进度和下一首控制只能使用其实际开放能力。区分“站内路由切换不重建实例”和“跨平台无缝播放”。超时、拒绝嵌入或平台限制时提供明确的官方入口。

自查：真实手机、受限内容和切换页面时的结果，是否与页面文案一致？

## 6. 每日推荐、并发与后台任务

### R01：把时间变成可以测试的输入

上海时间 00:10 触发；业务日期由 Go 决定。测试注入时钟验证午夜边界和跨日恢复，不修改主机时间。容器需要提供 Go 可用的 IANA 时区数据，并检查 LoadLocation 错误。

当天尚无结果时的 API 行为提前写进契约，例如返回明确的“尚未生成”状态；不要在每个访客 GET 请求中重新抽取。启动补偿只补今天。

### R02：幂等依赖事务、锁和约束

定时、手动、启动补偿调用同一生成服务。先准备所需外部数据，再在同一数据库事务内取得当天的事务级 advisory lock，重新检查当天记录，读取候选、生成并保存完整结果。已有结果直接读取；唯一约束作为最后保护，冲突路径也要正确收尾。

不能对一条还不存在的推荐记录简单使用行锁，就认为同日并发被串行化；也不能把连接级锁误当作事务级锁。参考 [PostgreSQL 显式锁](https://www.postgresql.org/docs/current/explicit-locking.html)。

自查：两个并发触发、服务重启、子项失败回滚后，今天是否仍只有一组完整结果？

### R03：选择规则是纯逻辑，降级要能结束

将候选、近期历史、数量和可控随机来源作为输入；输出选择结果，不直接访问数据库。数量不足时逐步缩短排除窗口或减量；同日不重复，不用无限重抽凑够数量。调整推荐数量默认影响未来新生成结果，不回写今天。

自查：空库、只有 1 首、所有候选都在最近 7 天出现过、同歌手占多数时，函数是否按约定结束？

### R04：任务 ID 必须对应真实可观察的执行

HTTP 返回任务 ID 前记录任务；后台执行使用受控 context，持久保存状态。进程意外退出后，遗留 running 状态需要在启动时识别并标记中断或按策略重试。重试有上限和间隔，错误摘要去敏，不用无限循环压平台接口。

单站点不必引入消息队列，但必须能解释接单、执行、失败、退出和恢复。来源不支持同步时，能力声明和管理页面直接说明；不返回虚假的同步成功。

## 7. 工程、部署与验证

### P01：保持学习改动可追踪

一次只做一个目标；先查看 diff 再由你提交。前端只选一种 package manager，保留对应锁文件。Go 使用 gofmt，前端使用现有类型检查与构建。学习练习、生成产物与正式代码注明用途；不自动删除文件。

### P02：明确配置位置和请求路径

前端公开配置不能包含数据库密码、会话密钥或隧道凭据。正式服务使用受限环境配置；Compose 内部通信使用服务名，容器 localhost 指向自己。确认 Nginx 的 API 路由、上传/正文大小、超时和可信代理，数据库不对公网开放。

自查：浏览器实际发出的 URL 是什么？Nuxt SSR 发出的 URL 是什么？数据库文件存在哪个卷？

### P03：先验证恢复，再称为可维护上线

备份保存到受控位置并有异机副本，恢复到独立数据库实际核对。发布前备份、记录镜像版本与迁移；数据库结构不兼容时不能只换回旧镜像。使用现有 Debian 主机前重新核对资源和端口，不使用原方案的历史数字代替当前状态。

文件、卷、测试数据库、试验容器和备份列出名称、位置、用途及是否仍需要；未经用户要求和对应确认不做破坏性清理。

### T01：测试业务风险，并且亲手解释测试

优先验证：草稿和管理权限、文章发布链路、PATCH 空值、来源失败保留数据、推荐边界、数据库并发幂等及恢复。样式小改动可手工检查，不为每一行代码复制一份镜像测试。

Go 的纯规则用 table-driven tests；HTTP 层用适当的请求测试；数据库约束和锁使用独立 PostgreSQL 验证。前端类型检查、构建与浏览器行为各有作用，不能互相替代。需要 race 检查时先确认工具链支持，Windows 环境问题不等同于业务代码有 race。

自查：测试失败时能说清哪条业务保证被破坏；测试通过时也能说明没有覆盖什么。

## 8. 每次请求 Review 前的五个问题

1. 我能说清楚这个改动的输入、输出和主要数据流吗？
2. 成功、空输入、失败各检查过至少一种情况吗？
3. 状态由谁维护，错误在哪里处理，权限由哪里验证？
4. 相关类型检查、构建或业务测试是否实际运行，并记录了结果？
5. 是否出现了新文件或试验资源，它们是否仍有用途？

助手 Review 时会以“文件/行号 → 触发条件 → 问题原因 → 你可以尝试的修正方向”的形式给反馈。没有发现实际问题时明确说明，不为凑数量虚构代码缺陷，也不直接替你修改实现。
