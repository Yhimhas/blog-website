# 个人网站开发方案与制作周期

版本：v1.0 · 规划日期：2026-09-13

本方案用于确认设计和组织后续开发。本次只编写方案，不安装服务、不创建隧道、不改动现有网站或容器。

## 1. 目标与默认范围

建设前后端分离的个人网站，包含博客、来自个人曲目清单的每日音乐推荐，以及可以继续增加功能的基础结构。

默认假设：一个站长管理网站；访客无需登录；每天向所有访客展示同一组推荐；曲目来源为网易云或 Bilibili；部署到现有 Debian 主机，通过 Nginx 和域名访问。具体语言熟练程度、视觉风格、每周投入时间尚未确定，工期按有基础的个人开发者与 AI 协作估算。

第一版交付：

- 首页、关于页、博客列表、文章详情、分类和标签。
- 站长登录；文章草稿、预览、发布、修改和归档；Markdown 编辑。
- 音乐页面、曲目来源管理、每日推荐、最近推荐记录。
- 按来源能力提供站内嵌入播放器或官方播放入口；站内可嵌入播放器放在持久布局中，减少文章切换导致的重载。
- 响应式布局、基础 SEO、HTTPS、服务自动启动、日志和备份恢复说明。

后续版本再增加：访客账号、评论和审核、访客收藏、统计看板、相册、书影音记录、更多音乐来源及个性化推荐。第一版无需 Redis、消息队列、微服务或机器学习推荐系统。

## 2. 技术选型

| 层次 | 选择 | 原因 |
|---|---|---|
| 前端 | Nuxt + Vue 3 + TypeScript | 适合博客 SEO、页面渲染、交互式音乐组件和后续页面扩展 |
| 前端状态 | Pinia，主要用于播放器 | 保存当前曲目、队列、播放偏好；避免把所有接口数据都放进全局状态 |
| 后端 | Go + Gin | 适合 API、定时任务和集成逻辑，部署为独立服务，维护成本可控 |
| 数据库 | PostgreSQL | 文章、曲目、推荐结果和管理账号都使用关系模型，事务与唯一约束可保证一致性 |
| 数据访问 | GORM | 提高第一版开发效率；复杂推荐查询可写参数化 SQL |
| 数据迁移 | golang-migrate + 版本化 SQL | 生产发布有明确的迁移记录，不依赖启动时 AutoMigrate 隐式修改数据库 |
| API 契约 | OpenAPI，接口前缀 `/api/v1` | 前后端明确字段和错误格式，生成 TypeScript 类型，减少联调偏差 |
| 部署 | Docker Compose + Nginx | 单机维护方便，前后端、数据库独立运行 |
| 推荐调度 | Go 内部调度器 + PostgreSQL 状态 | 单实例足够；通过日期唯一约束和数据库锁防止重复执行 |

Go 完全能胜任这个规模。主要难点是平台播放能力、产品体验和数据维护，语言性能不会成为第一阶段的主要限制。

选择 Nuxt SSR 意味着服务器上仍会运行一个 Node 进程，它只负责前端页面渲染；认证、业务规则、数据库访问和推荐任务都在 Go 中。浏览器使用同域 `/api/v1`，Nuxt 在服务端渲染时通过 Docker 内部地址访问 Go API，两端共用业务接口。不要把业务逻辑复制到 Nuxt server routes。

如果以后希望部署时完全不运行 Node，可以切换为静态生成；但新增或更新博客时需要触发重新构建。第一版采用 SSR，并对公开页面和公开 API 做适当缓存。

## 3. 部署结构

```text
访客浏览器
    │ HTTPS
    ▼
域名 + 已选定的公网接入方式
    │
    ▼
Nginx（唯一网站入口）
    ├── /api/v1/* ───────► Go API ─────► PostgreSQL
    └── 其他页面/静态资源 ► Nuxt SSR
                              │
                              └── 内部调用 Go API

Go API 进程内：每日调度器 → 来源适配器 / 推荐服务 → PostgreSQL
```

- 采用模块化单体：先运行一个 Go 服务，在代码中按博客、音乐、推荐、认证分模块。
- Nuxt、Go 和 PostgreSQL 放在 Docker 内部网络；正式部署不把数据库端口发布到公网。
- Nginx 的回源端口在实施前重新检查；此前主机 8080 已被占用，不直接套用教程端口。
- 可以使用现有 natfrp 的 host 网络回源到绑定在 `127.0.0.1` 的 Nginx 端口。若以后用容器化 cloudflared，优先通过容器服务名访问 Nginx；容器内的 localhost 通常不是主机。
- 不把 SSH、现有 AstrBot 或 natfrp 管理接口纳入网站路由。

公网接入选择：

| 方案 | 配置方式 | 适用判断 |
|---|---|---|
| Sakura Frp 香港 HTTPS 建站节点 | 域名 CNAME → 香港建站节点 → Nginx HTTPS；用 DNS 验证签发并自动续期可信证书 | 优先复用已购买套餐，需实测本地与访客网络体验 |
| Cloudflare Tunnel | 域名接入 Cloudflare DNS → cloudflared → Nginx；Cloudflare 管理访客端证书 | 维护证书方便，可作为备选，同样需要实测国内访问效果 |

2026-09-11 已只读确认 natfrp 账户为青铜 VIP、24 Mbps、当时可用流量约 154.3 GiB，且有香港建站节点可选；这些是检查时的状态，不能当作发布当天的剩余额度或稳定性保证。还需在实施前核实套餐到期时间、隧道数量上限和当前余量。

## 4. 代码组织与边界

前后端可以放在同一个 Git 仓库中，独立构建、独立部署，这不影响前后端分离。

```text
personal-site/
├── frontend/
│   ├── app/
│   │   ├── pages/                 # 首页、博客、音乐、管理页面
│   │   ├── layouts/               # 公共布局与管理布局
│   │   ├── components/
│   │   │   ├── blog/
│   │   │   └── music/             # PlayerShell、来源播放器
│   │   ├── composables/           # API 请求封装、分页等
│   │   └── stores/player.ts       # 播放队列与偏好
│   ├── nuxt.config.ts
│   └── Dockerfile
├── backend/
│   ├── cmd/api/main.go            # 初始化依赖、启动服务、优雅退出
│   ├── internal/
│   │   ├── auth/                  # 站长认证与会话
│   │   ├── blog/                  # 文章、分类、标签、发布规则
│   │   ├── music/                 # 曲目、清单、播放能力
│   │   │   └── provider/          # manual、netease、bilibili
│   │   ├── recommendation/        # 每日选择策略、推荐记录
│   │   ├── scheduler/             # 定时执行与启动补偿
│   │   ├── settings/              # 站点配置与功能开关
│   │   └── platform/              # 配置、数据库、日志、HTTP 中间件
│   ├── migrations/               # 编号 SQL 迁移
│   ├── go.mod
│   └── Dockerfile
├── api/openapi.yaml              # 前后端接口契约
├── deploy/
│   ├── compose.yaml
│   ├── nginx/site.conf
│   └── env.example               # 只包含变量名和非敏感示例
└── docs/                          # 本地运行、发布、备份与恢复说明
```

各业务模块按需使用 `handler.go`、`service.go`、`repository.go`、`model.go`：handler 处理 HTTP 参数和响应，service 管理业务规则，repository 访问数据库。不要为了目录整齐给每张表都生成多层无实际作用的抽象。

只有一个来源适配器接口需要提前稳定下来，示意如下，具体字段在第一阶段确定：

```go
type Provider interface {
    Capabilities() Capabilities
    Sync(ctx context.Context, source Source) (Snapshot, error)
    ResolvePlayback(ctx context.Context, item MusicItem) (Playback, error)
}
```

`Capabilities` 明确是否支持自动同步和嵌入播放。`Playback` 返回播放方式、经过校验的官方嵌入地址或官方跳转地址。某平台不支持某项能力时，界面展示对应入口，不假装拥有可用的音频直链。

## 5. 数据库与 API 规划

核心数据表：

| 表/表组 | 关键内容 |
|---|---|
| `admin_users`、`sessions` | 单站长账号、密码哈希、会话哈希、过期时间；不做公开注册 |
| `posts` | 标题、唯一 slug、摘要、Markdown、封面、草稿/发布/归档状态、发布时间 |
| `categories`、`tags`、`post_tags` | 分类与标签关联 |
| `music_sources` | 来源类型、来源 ID、同步方式、最近成功时间、状态 |
| `music_items` | 来源平台、平台内容 ID、标题、歌手或 UP 主、封面、官方地址、可用状态 |
| `source_items` | 清单与曲目的关联、顺序、启用状态；同一内容可属于多张清单 |
| `daily_recommendations`、`daily_recommendation_items` | 业务日期、算法版本、生成时间、推荐内容和排序 |
| `site_settings`、`job_runs` | 站点展示配置，以及同步/推荐任务的执行状态和错误摘要 |

曲目使用 `(provider, external_id)` 唯一约束，避免重复导入。同一 Bilibili 视频内的不同分 P 需区分页码或 cid。网易云与 Bilibili 上的相同歌曲，在无法可靠识别时允许保留为不同条目。

每日推荐以 `Asia/Shanghai` 的业务日期为唯一键；时间戳统一用 UTC 保存。推荐主记录及子项在同一事务内保存，避免页面读到不完整的一组推荐。

示例接口：

| 访问级别 | 方法与路径 | 用途 |
|---|---|---|
| 公开 | `GET /api/v1/posts` | 只返回已发布文章，分页和筛选 |
| 公开 | `GET /api/v1/posts/{slug}` | 文章详情，草稿不经公开接口泄露 |
| 公开 | `GET /api/v1/music/recommendations/today` | 返回今天固定的一组推荐 |
| 公开 | `GET /api/v1/music/recommendations?date=...` | 最近推荐历史，限制查询范围 |
| 公开 | `GET /api/v1/music/items/{id}/playback` | 返回允许的播放方式；限制请求频率 |
| 站长 | `POST /api/v1/admin/session` | 登录 |
| 站长 | `POST /api/v1/admin/session/logout` | 注销并使会话失效 |
| 站长 | `POST/PATCH /api/v1/admin/posts...` | 创建、修改、发布或归档文章 |
| 站长 | `POST/PATCH /api/v1/admin/music/sources...` | 配置清单和来源 |
| 站长 | `POST /api/v1/admin/music/sources/{id}/sync` | 触发支持的来源同步，返回任务 ID |
| 站长 | `GET /api/v1/admin/jobs/{id}` | 查看任务结果 |

公开接口只返回展示所需信息；所有写接口由 Go 验证会话和权限。响应使用一致的错误码、说明和 request ID，不返回 SQL 错误或敏感配置。分页设置上限，参数查询使用绑定值。

## 6. 网易云与 Bilibili 的实现策略

音乐功能分成三件事，各自验证：读取曲目清单、每天选择推荐、让访客播放。取得元数据不代表拥有完整音频播放能力。

第一阶段验证矩阵：

| 能力 | 网易云 | Bilibili |
|---|---|---|
| 输入来源 | 用户给定歌单或歌曲 ID | 用户给定视频/BVID 清单、收藏夹或合集；不是所有入口都保证可同步 |
| 自动读取清单 | 验证官方可用接口、访问条件与权限 | 验证官方可用接口、公开性、分页与权限 |
| 站内播放 | 验证平台允许的嵌入方式和曲目限制 | 优先验证官方视频嵌入；不预设可独立抽取纯音频 |
| 移动端行为 | 验证登录、会员、浏览器交互限制 | 验证登录、地区、移动端嵌入限制 |
| 失败降级 | 显示曲目信息和官方播放入口 | 显示视频信息和官方播放入口 |

若自动读取接口不适用，第一版提供手动维护曲目 ID/官方链接清单的能力，每日推荐仍可自动执行；持续自动跟随远端歌单变化属于单独的同步能力，只有验证通过后才列入已承诺功能。

不把第三方逆向 API、会员 Cookie、绕过登录或版权限制、永久有效音频地址作为上线基础。第三方集成失败时保留最后一次成功的数据，记录同步时间和错误，不清空整张曲目表。平台缩略图和媒体内容只按允许的方式使用。

如果你要求“全部曲目都能在自制播放器中完整、无缝、纯音频播放”，需要先通过播放能力验证再确认范围和工期；官方嵌入或跳转不能视作该要求已经实现。

## 7. 每日推荐与播放器行为

第一版默认每天推荐 3 首，所有访客一致，可在设置中调整数量。

推荐规则：从启用且可用的曲目中选择；优先避开最近 7 天推荐过的内容，尽量避免同一歌手连续出现。曲库太小时逐步缩短排除窗口或减少推荐数量。同一条目在同一天不重复。无需引入 AI 即可实现稳定、可解释的推荐。

任务执行流程：

1. 每天 00:10（Asia/Shanghai）运行；如来源支持自动同步，先同步并设置超时，失败则使用最后成功的数据。
2. 获得当天任务的数据库锁，再检查当天结果是否已存在；已有结果则直接结束，不重新抽取。
3. 根据候选集和近期记录生成推荐，在事务中保存完整结果。
4. 保存成功/失败摘要；设置有限次数重试，避免平台故障时持续高频请求。
5. 服务启动时检查今天是否缺少结果并补做。主机跨日关机恢复后只补今天，不伪造过去几天“已经发布”的记录。

进程内调度触发器在单实例下即可使用；推荐服务必须通过数据库锁和唯一约束保证幂等，以便将来增加实例或手动重试。收到关机信号时停止接收新任务，限时等待任务完成。

播放器使用固定的 `PlayerShell` 放在公共布局中，具体内部组件按来源切换。保留当前条目和音量偏好；官方 iframe 是否允许精确控制暂停、进度、下一首，以验证结果为准。浏览器通常需要用户首次点击才能有声播放，验收不要求打开网页后强行自动出声。跨路由不重载播放器与跨平台无缝播放是两项不同能力。

## 8. 工期、交付物和验收

以下是工作量估算，不是固定交付承诺。默认第一版接受验证通过的官方嵌入播放，以及无法嵌入时的官方跳转；不包含平台未开放的全曲解析能力。

| 阶段 | 预计工时 | 交付与验收条件 |
|---|---:|---|
| P0：需求与音乐验证 | 6–10 小时 | 页面范围、数据来源、播放能力矩阵、接口草案；明确哪些能力可承诺 |
| P1：工程基础 | 16–24 小时 | Nuxt/Go/PostgreSQL 联通、首批 SQL 迁移、站长登录、统一 API、开发启动说明 |
| P2：博客闭环 | 18–26 小时 | 创建草稿→预览→发布→公开访问→归档；分类标签、移动端、页面标题与摘要 |
| P3：来源与播放器 | 16–24 小时 | 清单管理、去重导入、来源适配器、曲目展示、验证通过的播放方式及失败入口 |
| P4：每日推荐 | 12–18 小时 | 定时生成、去重、曲库不足处理、启动补偿、历史展示和任务状态 |
| P5：发布与质量检查 | 12–18 小时 | Nginx、HTTPS、自启、关键测试、备份恢复演练、运行文档、外网与手机验证 |
| 基础合计 | **80–120 小时** | 完成第一版 |
| 20% 缓冲后 | **96–144 小时** | 用于联调、视觉修改和已验证集成的故障处理 |

| 每周有效投入 | 建议预留的日历周期 |
|---:|---|
| 15 小时 | 约 7–10 周 |
| 25 小时 | 约 4–6 周 |
| 40 小时 | 约 3–4 周 |

熟悉 Go 或 Vue 可以靠近下限；两者都在学习时，建议再预留学习时间。平台能力不开放属于范围限制，增加工期不一定能解决。

按每周 25 小时安排：第 1 周完成 P0、P1 和最小页面；第 2 周完成博客闭环；第 3 周完成音乐来源与播放；第 4 周完成每日推荐并进入部署；第 5–6 周用于联调、验收和缓冲。取得域名和账号配置可与开发并行，正式入口验证依赖这些条件完成。

可以在约第 2 周交付可浏览博客的本地版本，第 4–6 周完成完整第一版。具体起止日期在确定开始时间和每周投入后填写，不预设今天开始开发。

## 9. 注意事项与发布标准

**业务边界。** 每日推荐首先是“你挑选的内容轮换给大家看”，不是为每个访客计算个性化推荐。网易云与 Bilibili 的账号体系、媒体格式和播放能力不能视为统一。

**博客渲染。** Markdown 渲染进行 HTML 清洗，默认不执行任意嵌入脚本或 MDX 代码。公开 API 排除草稿；草稿预览使用受保护的管理页面，并禁止搜索引擎索引。

**账号与来源地址。** 使用成熟密码哈希库和不可预测的会话 token；数据库只保存 token 哈希。生产 Cookie 设置 HttpOnly、Secure、合适的 SameSite，写请求配合 CSRF/Origin 校验。URL 导入只识别受支持平台的 ID，不提供任意地址代理，防止来源抓取访问到主机内网服务。

**缓存与代理。** 只缓存公开数据，管理接口、草稿和会话响应禁止共享缓存。Nginx 和应用只信任已配置的代理，避免随意相信外部传入的 X-Forwarded-*。SSR 请求私有数据时正确处理会话，不把站长 Cookie 或私有接口结果缓存给其他访客。

**凭据。** 域名 DNS API token、数据库密码和隧道凭据使用受限配置，不提交 Git、不进入前端构建产物、不写入日志。开发和正式部署的配置分开。

**资源与存储。** 此前本机剩余磁盘约 20 GB，实施前重新检查。第一版优先保存文章、元数据和少量站点图片；不把主机当作音乐或视频下载仓库。Docker 镜像、日志和备份会占用空间，需要观察用量。

**备份与恢复。** 每日备份 PostgreSQL，备份站点配置和自有上传资源；至少有一份存放在这台主机以外。必须实际恢复到独立测试数据库验证。备份保留周期需另行确定，默认不自动删除旧备份。

**发布流程。** 构建镜像→备份→审核并执行版本化迁移→更新服务→健康检查→浏览器验证。保存上一版镜像引用以便回退；破坏性数据库迁移不能简单靠换回旧镜像恢复。第一版允许明确安排短暂维护窗口，不承诺零停机发布。

**测试重点。** 自动化验证草稿权限与管理接口、每日推荐并发幂等和跨日、来源超时保留历史数据；对文章发布流程和播放器导航进行浏览器验证。Docker 自启策略核对后，在合适维护窗口验证服务重启；不为测试突然重启整台正在使用的主机。

**文件约束。** 遵循你的要求，不自动删除任何文件。文章先做归档；测试文件、日志、试验容器和数据库等中间产物逐项列出。文件清理、Docker 卷删除或破坏性数据库操作不作为默认发布步骤，需单独按你的要求确认。

上线验收清单：

- 外网和手机可通过域名以 HTTPS 访问；证书自动续期方式已配置并检查。
- 站长可发布文章，普通访客无法读取草稿或修改数据。
- 今天的推荐在刷新、并发请求和服务重启后保持一致。
- 来源接口不可用时，已发布博客和已有推荐仍可访问。
- 可播放内容按验证结果运行，受限内容有清楚的官方入口。
- 容器异常后可自动恢复；应用日志中没有密钥和密码。
- 数据备份可以恢复，发布说明和残留清单已交付。

## 10. 开发顺序与待确认项

实施顺序固定为：音乐能力验证 → 前后端骨架 → 博客闭环 → 音乐来源和播放器 → 每日推荐 → 正式部署。

开始开发时最需要确认的内容：真实歌单/视频清单；是否接受官方嵌入或跳转；文章编辑方式；站点名称和视觉偏好；每周可投入时间。这些会影响范围或估期，域名可以稍后购买。

第一版之后，优先增加评论审核与站点搜索，再按实际使用增加相册、书影音或访客功能。新功能先放入独立 Go 模块，复用认证、数据库和 API 规范；只有出现独立部署、显著负载或独立团队需求时，再考虑拆服务。
